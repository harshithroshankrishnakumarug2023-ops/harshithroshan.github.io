# Harshith Roshan — Academic Website

A minimal, professional personal academic website: research portfolio, web resume,
publication and project archive, and document library.

Built as a **static site** and deployed to **GitHub Pages**. No backend, no
database, no build server, no paid services, no third-party JavaScript.

- **Live site:** `https://harshithroshankrishnakumarug2023-ops.github.io/harshithroshan.github.io/`
- **Repository:** `https://github.com/harshithroshankrishnakumarug2023-ops/harshithroshan.github.io`

## 2. How it works

The site is generated by a small Python script (`build.py`). It reads the JSON
files in `content/`, turns them into HTML pages, copies your documents from
`public/` into place, and writes everything into `dist/`.

```
content/*.json  +  public/**  +  src/styles + src/scripts
                       |
                 python build.py
                       |
                     dist/          <- this folder is what GitHub Pages serves
```

Three consequences worth knowing:

- **You never edit HTML.** Pages are rendered from content files, so adding a
  project or a document means editing JSON, not markup.
- **Every link is relative.** The site works at `/`, at `/my-repo/`, or from a
  local folder — no base-path configuration to get wrong.
- **There are no dependencies.** Standard Python only, nothing to install,
  nothing that can break with a package update.

Pages are built with `src/styles/main.css` and `src/scripts/main.js`. The
JavaScript is progressive enhancement only: navigation, filtering and search all
degrade gracefully if it never loads.

## 3. Local setup

You need **Python 3.9 or newer**. Check with `python --version`.

```bash
# Build the site into dist/
python build.py

# Build and preview at http://localhost:8000
python build.py --serve
```

The build prints a link check:

```
Built 16 files into .../dist
All local links resolve.
```

If you add a document entry before uploading the file, the build reports the
missing path and exits with an error, so a broken link can never reach the live
site. While drafting, `python build.py --allow-broken-links` skips that check.

To preview changes in a browser, edit a content file, then re-run
`python build.py --serve` and refresh the page.

> Editing files locally requires a text editor. [Visual Studio Code](https://code.visualstudio.com/)
> is free and shows JSON errors clearly.

## 4. Deploying to GitHub Pages

The repository already contains the workflow `.github/workflows/deploy.yml`.
Once, in GitHub:

1. Push this project to the repository
   `harshithroshankrishnakumarug2023-ops/harshithroshan.github.io` (main branch).
2. Open **Settings → Pages**.
3. Under **Source**, choose **GitHub Actions** (not "Deploy from a branch").
4. Save. The first deployment starts automatically.

Every later `git push` to `main` rebuilds and republishes the site. The Actions
tab shows the build; if it fails, the reason is printed there.

The workflow:

1. checks out the repository,
2. sets up Python,
3. runs `python build.py` (including the link check),
4. uploads `dist/` as the Pages artifact,
5. publishes it to GitHub Pages.

**About your address.** Because the repository name (`harshithroshan.github.io`)
differs from the account name, GitHub serves the site from a sub-folder:

```
https://harshithroshankrishnakumarug2023-ops.github.io/harshithroshan.github.io/
```

That is already recorded in `content/site.json` as `baseUrl` (used only for
canonical links, Open Graph tags and the sitemap), and all internal links are
relative, so the site works unchanged.

If you later add a **custom domain**, put the domain in a `CNAME` file at the
repository root, point DNS at GitHub's servers, enable "Enforce HTTPS", and
update `baseUrl` in `content/site.json` to `https://yourdomain.com/`.

## 5. Repository structure

```text
/
├── build.py                     # the generator: python build.py
├── sitegen/                     # generator source
│   ├── core.py                  #   content loading, URLs, layout components
│   └── pages.py                 #   one function per page
│
├── content/                     # ← YOU EDIT THIS (all text lives here)
│   ├── site.json                #   name, tagline, navigation, links, footer
│   ├── home.json                #   homepage introduction and research themes
│   ├── about.json               #   biography, education, research & clinical experience
│   ├── skills.json              #   skills (shared by About and Resume)
│   ├── research.json            #   research page introduction
│   ├── resume.json              #   resume page sections and download link
│   ├── documents.json           #   document library index
│   ├── publications.json        #   publications and manuscripts
│   ├── writing.json             #   academic and public writing
│   └── projects/                #   one JSON file per research project
│       ├── _template.json       #     copy this to start a new project
│       └── <your-project>.json
│
├── public/                      # static files, copied verbatim to the site root
│   ├── documents/               #   your PDFs and other files
│   │   ├── resume/
│   │   ├── research/
│   │   ├── proposals/
│   │   ├── writing/
│   │   └── other/
│   │       # a category needs both a folder here and an entry in
│   │       # content/documents.json → "categories"
│   ├── images/
│   └── favicon.svg
│
├── src/
│   ├── styles/main.css          # the entire design system
│   └── scripts/main.js          # mobile menu + document filtering
│
├── .github/workflows/deploy.yml # automatic deployment
├── dist/                        # build output (generated, not committed)
└── README.md
```

Every content file starts with a `_readme` key explaining its own fields. Keys
beginning with `_` are ignored by the build, so you can leave instructions in
place.

## 6. Changing your personal information

Edit **`content/site.json`**:

| What | Key |
| --- | --- |
| Your name | `name` |
| Short role, shown in the footer | `role` |
| Line under your name | `tagline` |
| Browser title | `siteTitle` |
| Site description (SEO) | `siteDescription` |
| Navigation items and order | `nav` |
| Footer year | `copyrightYear` |
| Live address (SEO, sitemap) | `baseUrl` |

Edit **`content/home.json`** for the homepage introduction, research themes and
section headings. Edit **`content/about.json`** for the biography, education and
research experience.

Text in square brackets — for example `[Your intended focus]` — is a placeholder.
It is displayed in a muted style until you replace it. Plain text supports three
small conveniences:

- `[label](https://example.com)` becomes a link
- `https://example.com` on its own becomes a link
- `*emphasis*` becomes italics

## 7. Updating the resume

The web resume is assembled from three files:

1. **`content/resume.json`** — resume-only sections (Research Experience, Clinical
   Experience, Positions of Responsibility, Awards, …), the download button, and
   the "Last updated" date.
2. **`content/about.json`** — Education is taken from here, so it appears on
   both pages at once.
3. **`content/projects/*.json`** — Research Projects are generated automatically.

To add a resume entry, append an object to the relevant section in
`content/resume.json`:

```json
{
  "id": "research-experience",
  "title": "Research Experience",
  "items": [
    {
      "title": "Lab or institution name",
      "subtitle": "Research assistant",
      "date": "2025 – 2026",
      "body": "Research area, in one line.",
      "bullets": [
        "What you designed or ran",
        "What you analysed"
      ],
      "links": [
        { "label": "Protocol", "file": "documents/research/protocol.pdf" }
      ]
    }
  ]
}
```

Rules:

- Sections appear **in the order they are listed** in `content/resume.json`, so
  you can reorder or delete them freely.
- A section either pulls in shared content — `"source": "education"`,
  `"source": "projects"` or `"source": "skills"` — or holds its own `items`.
  This is why Education, Research Projects and Skills never fall out of sync
  with the About page.
- A section with **no items and no `emptyState`** is not shown at all — this is
  how sections stay off the page until you have something to put in them. To
  hide a section that currently only shows a placeholder sentence, delete its
  `emptyState` line.
- `"showEducation"`, `"showProjects"` and `"showSkills"` at the top of the file
  switch those three shared sections off entirely.
- Update `"lastUpdated"` (for example `"October 2026"`) whenever you edit the
  resume.

### The resume PDF

Replace the file `public/documents/resume/Harshith_Roshan_Resume.pdf` with a
newer version of your resume PDF (keep the filename, or change `download.file` in
`content/resume.json`). Keep only one current resume in the repository so there
is never any doubt about which version is current.

## 8. Adding a research project

1. Open `content/projects/_template.json`.
2. **Save a copy** next to it as e.g. `content/projects/emotional-memory.json`
   (no leading underscore in the filename).
3. Fill in `slug` — this becomes the address `/research/<slug>/`.
4. Fill in the title, short description, question and background.
5. Fill in the `method` fields. Anything left empty or as `[bracketed text]` is
   either hidden or shown as an obvious placeholder.
6. Run `python build.py`.

The project appears automatically on the research page, on the homepage if you
set `"featured": true`, and on the resume page.

If new information turns out to describe a project you already have, edit that
project's JSON rather than creating a second file for it.

Status is free text; useful values are `Conceptualization`, `Data collection`,
`Analysis`, `Manuscript preparation`, `Completed`. Use whatever matches reality.

## 9. Adding a publication

Edit **`content/publications.json`** and add an entry to `entries`:

```json
{
  "category": "manuscripts",
  "authors": "Roshan, H., & Author, A. A.",
  "year": "2026",
  "title": "Title of the paper",
  "venue": "Journal Name",
  "status": "Under review",
  "doi": "",
  "links": [
    { "label": "PDF", "file": "documents/research/paper.pdf" }
  ],
  "externalUrl": ""
}
```

`category` must be one of the ids listed in the same file: `publications`,
`manuscripts`, `working-papers`, `reports`. Publications appear on the research
page and on the homepage. Until the first entry exists, the pages show a short
empty state instead of an empty section.

```json
{
  "category": "academic",
  "title": "Title of the piece",
  "date": "2026",
  "type": "Literature review",
  "publication": "Course, institution",
  "description": "One or two sentences about the piece.",
  "url": "",
  "file": ""
}
```

`category` is one of `academic`, `science-communication`, `public`,
`coursework`. Use `url` for something published elsewhere, or `file` for a PDF
stored in `public/documents/writing/`.

## 11. Adding a PDF or other document

Two steps, and the document appears in the library with working View and
Download buttons.

**Step 1 — put the file in the right folder** under `public/documents/`:

| Folder | For |
| --- | --- |
| `resume/` | your CV / resume |
| `research/` | papers, reports, manuscripts, datasets |
| `proposals/` | research proposals, protocols, preregistrations |
| `writing/` | written work not published elsewhere |
| `other/` | anything else |

Add a new category by creating the folder **and** adding it to
`content/documents.json` → `categories`.

**Step 2 — add an entry** to `content/documents.json`:

```json
{
  "title": "Childhood Emotional Abuse, Emotional Neglect, and Inhibitory Control",
  "description": "A research proposal examining the relationship between childhood psychological maltreatment and inhibitory control in emerging adults.",
  "type": "Research Proposal",
  "category": "proposals",
  "year": "2026",
  "file": "documents/proposals/ICSSR_Thesis_Research_Proposal.pdf",
  "tags": ["Undergraduate thesis"],
  "project": "childhood-maltreatment-inhibitory-control"
}
```

- `category` should match the folder name.
- `file` is the path **inside `public/`** — this is the single most common
  mistake; the build will tell you if the path does not exist.
- `type`, `year`, `tags` are shown in the listing and can be filtered.
- `project` links the document to a research project (optional).

**View versus Download.** PDFs and images get both buttons: *View* opens the
file in a new browser tab (so it can be read without downloading), *Download*
saves it. Other file types — DOCX, PPTX, XLSX, CSV, TXT, ZIP, PsychoPy
experiment files, code, datasets — get a *Download* button only. No fake
previews are invented for files a browser cannot display.

You can also link documents from a research project by adding them to that
project's `documents` list in its JSON file.

## 12. Changing the visual theme

Everything visual lives at the top of **`src/styles/main.css`**:

```css
:root {
  --font-sans:  "Inter", ...;            /* navigation, labels, buttons, metadata */
  --font-serif: "Source Serif 4", ...;   /* body text and headings */
  --paper:  #fdfdfb;                     /* page background */
  --paper-2: #f6f6f2;                    /* secondary surfaces, footer */
  --ink:    #1a1a18;                     /* main text */
  --ink-soft: #3a3a36;                   /* body copy inside entries */
  --muted:  #5c5c56;                     /* secondary text */
  --faint:  #6b6b64;                     /* metadata and placeholders (AA) */
  --rule:   #e3e3dd;                     /* hairline dividers */
  --rule-strong: #cfcfc6;                /* borders on buttons and chips */
  --accent: #1f4e6e;                     /* primary accent colour */
  --accent-deep: #2c6152;                /* second gradient stop */
  --measure: 36rem;                      /* line length of body paragraphs */
  --radius:  4px;                        /* corner rounding */
  --shadow-sm / --shadow-md / --shadow-lg /* depth, used sparingly */
}
```

- **Accent colour:** change `--accent` (with `--accent-dark` and
  `--accent-deep`). One accent only — that restraint is what keeps the site
  looking academic.
- **Fonts:** body text is set in **Source Serif 4** (a modern book serif, warmer
  and more legible than Times New Roman), while navigation, labels and buttons
  stay in **Inter** so the interface reads as a distinct layer. To use a
  different pairing, change `--font-sans` / `--font-serif` *and* update the
  Google Fonts URL in `sitegen/core.py` (`FONT_STACK`), or delete that line to
  fall back to system fonts.
- **Line length:** adjust `--measure` (36rem ≈ 70 characters).
- **Spacing:** the main scale values are in the `clamp()` expressions
  throughout the file; they already scale down on phones.
- **Gradients:** the page background, the featured-research panel, the primary
  button and the file-format chips use very low-contrast gradients defined in
  the tokens above and in the component rules. To flatten them, delete the
  `background-image` declarations in `body`, `.featured`, `.btn-primary`,
  `.doc-badge` and `.filters`.

### Images

- **Portrait:** `content/about.json` → `"portrait"` → `"file"`. It currently
  points at `images/portrait.jpg`. To use a different photograph, drop the file
  into `public/images/` and change the path; resizing to about 960 px on the long
  edge and saving as JPEG keeps the page fast. Delete the whole `portrait` block
  to remove the image entirely; on wide screens it sits beside the biography, and
  on phones it appears above it.
- **Social preview image:** drop a **1200 × 630** PNG or JPG into
  `public/images/` and set `"ogImage"` in `content/site.json`. While it is
  empty, no `og:image` tag is emitted and the share card falls back to the page
  title and description.
- Any other images can go in `public/images/` and be linked from content files
  with normal Markdown links, e.g. `[figure 1](images/figure-1.png)`.

## 13. Adding external links

Edit **`content/site.json`**:

```json
"links": {
  "email": "harshith.roshan@ashoka.edu.in",
  "linkedin": "https://www.linkedin.com/in/your-profile/",
  "github": "https://github.com/your-handle"
}
```

- An email address is automatically turned into a `mailto:` link.
- A link that is left empty (`""`) is shown as a muted placeholder such as
  `[LinkedIn]` rather than as a link, so nothing invented or broken ever
  appears on the site.
- These links feed the homepage, the footer and the contact page.

Project-specific links (pre-registrations, code repositories) belong in the
project's `externalLinks` list instead.

## 15. Privacy and unpublished materials

**Everything in this repository is public.** GitHub Pages makes `public/`
readable by anyone with the URL, and GitHub shows the raw file contents too.
Unpublished manuscripts, participant data, consent forms, interview material or
anything confidential should not be in this repository at all.

Worked examples of what has been deliberately left out, so it does not get added
by accident later: raw PsychoPy experiment folders and their trial data, image
stimulus sets for the thesis and the eye-tracking study, coded adolescent
referral data from the Family Journeys Co-Lab (de-identified, but still clinical
material about real people), and any phone number. If you want a document
published, add it to `public/documents/` deliberately.

Controls available to you:

- **Do not upload it.** The simplest option — nothing on the site can link to a
  file that is not in the repository.
- **Omit it from the library.** Adding `"private": true` to an entry in
  `content/documents.json` removes it from the listing, filters and search. The
  file itself is still reachable by direct URL, so use this only for files you
  are willing to publish but do not want listed.
- **Describe without linking.** Point to "available on request" in the
  description text instead of to a file.

For confidential work, use a separate private repository with its own access
controls, or share documents through your institutional system.

## 16. Troubleshooting

**"Build failed. Fix the paths above"** — a document or project entry points at
a file that does not exist in `public/`. The message names the exact entry. Either
upload the file or correct the `file` path.

**The site does not update after a push** — open the repository's **Actions**
tab and check the latest run. If Pages is set to "Deploy from a branch" instead
of "GitHub Actions", the workflow's output is ignored: change it under
**Settings → Pages**.

**A link works locally but not on GitHub Pages** — check that the target file
is committed in `public/` and that the `file` path starts with
`documents/…`, with no leading slash and no machine-specific characters.

**I want to change the fonts** — see section 12; two places are involved
(`src/styles/main.css` and the `FONT_STACK` constant in `sitegen/core.py`).

**I want to add a page** — add a function to `sitegen/pages.py` that returns a
page via `render_page(...)`, then register its output path in the `built` list
in `build.py`. Add the same path to `nav` in `content/site.json`.

**I want to preview without Python** — open `dist/index.html` in a browser.
Pages are plain files and links are relative, so everything works, including the
PDFs.
